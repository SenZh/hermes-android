# 变更日志 (Changelog) 编写规范与工程范式

本文档沉淀自 `v1.9.0` 发布实践与 OpenChamber 等工业级开源项目的 Release Notes 标准。
供后续所有版本发版（包括团队协作、开源维护与外部贡献）严格遵循。

---

## 核心定位与原则

### 1. 拒绝两极分化
- **严禁流水账与过度口语化（大白话）**：诸如“以前点这里会报错，现在修好了”、“以前卡死，现在顺畅了”。这种写法缺乏工程事实、可验证性与专业度。
- **严禁纯 Git 提交堆砌与晦涩黑话**：不要直接甩 Git 提交信息（如 `fix(scope): minor fix` 或生造抽象概念），必须面向“专业工程师与高级用户”交付高质量信息。
- **标准尺度**：“**说人话，但不说大白话**”。保持高密度的技术准确度（模块名、API 名、参数名、异常类名），用清晰的因果链推导逻辑阐述。

---

## 骨架结构 (Structure)

每次正式发版必须按三层板块划分：

```markdown
## [版本号] - YYYY-MM-DD

简述统计：自上一正式版 vX.Y.Z 以来共计 N 个提交、M 个源码文件变更（+Insertions / −Deletions 行）。

---

### 新增功能 (New Features)
- **模块/功能粗体导读 (Feature Name)**：具体阐述...

### 体验优化与界面重排 (Improvements)
- **体验改动粗体导读 (UX/DX Item)**：具体阐述...

### 缺陷修复 (Bug Fixes)
- **缺陷现象与成因简述 (Issue / Crash Name)**：具体阐述（按 5W2H 格式）...

---

### 线上入口 / 构建产物
- Release 页面、安装包直链及校验信息
```

---

## 词条编写语法规范 (Syntax & Content)

### 1. 词条标题强制加粗 (Lead-in Tag)
每个列表项第一句必须是加粗的模块或功能主题标签，中英双语结合最佳：
- ✅ `- **图片手势查看器 (Image Viewer)**：全面替换原静态组件...`
- ✅ `- **下载链路堆内存溢出 (OOM Fix)**：根治针对大文件...`
- ❌ `- 修了图片放大...`

### 2. 缺陷修复严格遵循“三段式因果链” (Symptom -> Cause -> Fix)
任何非微小的 Bug 修复，必须交代：
1. **现象/异常原文 (Symptom)**：如抛出的具体异常类名或直观系统现象（如 `OutOfMemoryError: Failed to allocate...` 或 `Only local file URLs are supported`）；
2. **底层机理/根因 (Root Cause)**：指出为何在特定环境/框架层出现（例如“SAF `getTreeDocumentId` 仅取根标识直接丢弃后续路径段”）；
3. **修复实施与状态跃迁 (Implementation & State Diff)**：精确交代改为了什么方案（例如“改由底层通道直写 SAF，二进制数据完全不经过 JS 堆内存”）。

### 3. 数据与硬实体支撑 (Hard Evidence)
涉及性能、尺寸、限制、生命周期时，必须带上客观数字与真实实体：
- 写入明确的数值量化（如“1x–5x 缩放”、“82MB 安装包”、“申请 227MB 连续内存”）；
- 写入精确的系统实体（如 `ACTION_VIEW`、`FLAG_GRANT_READ_URI_PERMISSION`、`MIME_TYPE_DIR`、`app.json`）。

## 防漏检查清单 (Checklist Before Publishing)

在定稿 Changelog 前，必须对照自查以下维度是否被遗漏：
- [ ] **视觉与交互重构**：侧边栏按钮排布、输入面板紧凑度、状态盾牌、长按复制与选区。
- [ ] **后台与生命周期**：前台服务保活策略、超时与重试时序、自动更新检查机制（如 1 小时轮询调度）。
- [ ] **平台与机型适配**：国产 ROM（小米/华为/OPPO/vivo/三星）保活、自启动与权限申请。
- [ ] **工程与构建基础设施**：`versionCode` / `versionName` 单一真源（SSOT）、签名配置（v1+v2）、CI 门禁与新增测试集。
- [ ] **国际化覆盖 (i18n)**：新增/补全的语言资源包。
