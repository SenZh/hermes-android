# 代码审查报告

审查对象：`main` @ `4aa83bd`（v1.8.3-preview.23）+ 前置提交 `28b9425`（ROM 适配）、`6dc493b`（openFile/openFolder）
审查方式：逐行读源码，Kotlin 部分按编译器替身做静态类型/语法核对（本地无 Android SDK），JS 侧实跑 `tsc --noEmit`（0 error）、`vitest run`（9 文件 / 84 用例全绿）、`eslint`（3 warning），并对照设计文档 requirements / tech-design / test-plan。

## 结论

**Reject**：两个宣称的核心能力在真机上都是死路径——图片手势回调在 worklet 里调用了非 worklet 的纯函数（首次捏合即抛 Remote Function 错误），openFolder / 自启动的 `resolveActivity` 探测在 targetSdk≥30 下被机型可见性过滤恒置为 null（四层降级退化成只剩最后一层），而 `tsc`、单测、`verify-fixes` 三道门禁全部放行，不能靠现有 CI 兜住。

## 逐维度审查记录

**1) 正确性**

手势语义层本身写得干净：`resolveSingleTap` 用 `> 1 + ε` 判"已放大"、`nextDoubleTapScale` 与它同向、`clampScale` 对 NaN/±Infinity 的处理（`imageZoom.ts:23-26`）与单测 TC-ZOOM-03 对得上，`clampTranslation` 的 `overflow ≤ 0 → 0` 与"内容小于容器锁死在原点"一致，`Gesture.Exclusive(doubleTap, singleTap)` 的组合顺序也正确（`ZoomableImage.tsx:88`）。但**接线层有两处语义失真**：`onEnd` 丢掉 `success` 参数（#5，RNGH 在 ACTIVE→CANCELLED 时确实以 false 回调，见 useAnimatedGesture.ts:157-161），以及捏合结束后不重算平移夹取（#4），导致"缩回 1x 后图片停在偏移位"。更根本的是 #1：这些纯函数在 UI 线程不可调用，正确性讨论在当前形态下都跑不起来——`resolveSingleTap` 的返回值永远拿不到。`viewer.tsx` 侧的全屏状态机在语义上没错（1x 单击进、全屏内 1x 单击出），但它依赖 #2 的容器，层级一错，交互全部错位。

**2) 并发与线程**

`runOnJS(onSingleTap)()` 的用法本身正确：`onSingleTap` 是父组件传入的 JS 闭包，在 worklet 里通过 `runOnJS` 跨到 JS 线程是官方范式，且该闭包只捕获 `setImageFullscreen`，无大对象序列化开销。`boxW.value`/`boxH.value` 在 `onLayout`（JS 线程）写、在 worklet 读，shared value 的跨线程读写是设计允许的，不存在撕裂（写入的是单个 float）。`toOrigin` 带 `'worklet'` 指令、只碰 shared value，被三个手势 worklet 捕获时走 `cloneWorklet` 正常。**唯一但致命的问题是闭包里那 5 个普通函数**：`getClosure`（plugin/index.js:700-728）把 `clampScale` 等当作普通闭包变量收集，序列化时命中 `serializable.native.ts:156-159 → cloneNonWorkletFunction`，在 UI 线程被替换成 `remoteFunctionUnpacker.native.ts:8-16` 的 throw guard。这不是"性能问题"，是每次手势都抛异常。Kotlin 侧的线程面没看出问题：`state`/`lastStartError`/`stopRequestedAt` 都是 `@Volatile`，watchdog 走主 Looper Handler，`OnDestroy` 有 `removeCallbacks`，`requestStop` 用时间戳而非布尔避免了 check-then-act 竞态（KeepAliveService.kt:141-159）——这一处设计是对的，唯一残留是 `UNCONFIRMED` 无回收路径（#19）。

**3) 生命周期与内存**

`imageFullscreen` 是纯 `useState`，页面卸载即随组件销毁，不存在跨页残留；`ZoomableImage` 没有注册任何事件监听/定时器，只持有 7 个 shared value，卸载后由 reanimated 自身回收，因此"全屏层状态是否会在页面卸载时残留"的答案是**不会**，理由是没有任何模块级单例或全局监听被写入。真正缺的是**反向**：全屏期间没有 `onRequestClose`/`BackHandler`，安卓返回键走的是路由 pop，会直接退出整个 viewer 而不是关层（viewer.tsx 全文无 BackHandler，同仓 `(tabs)/sessions.tsx:207` 有现成范式）。内存面上 #20 的双份解码与既有 `data_url` base64 预读叠加——注意这是既有问题（AGENTS.md「零内存 Base64 铁律」），本轮没有加重，但把"显示一张图"变成"显示两张"使峰值更差。

**4) Android API 正确性**

逐条核对后**判定正确的部分**：`DocumentsContract.isTreeUri` + `buildDocumentUriUsingTree(uri, getTreeDocumentId(uri))` 的用法完全正确（getTreeDocumentId 取 pathSegments[1]，正是前置知识里"后续段被丢弃"的那条坑，这里没有踩）；`PowerManager.isIgnoringBatteryOptimizations` + `Settings.ACTION_REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` + manifest 声明 `REQUEST_IGNORE_BATTERY_OPTIMIZATIONS`（AndroidManifest.xml:6）三件套齐备，minSdk≥24 所以无 API 23 守卫缺失问题；`foregroundServiceType="dataSync"` 与 `FOREGROUND_SERVICE_DATA_SYNC` 权限成对出现（Android 14+ 必需）；`Function("openFile")` 的第二参 `String?` 是合法的可空参数——我核对过 expo-modules-core 的参数装配（`AnyFunction.kt:67-71`：`requiredArgumentsCount` 只统计非空参数，缺省位补 null），因此 JS 侧传 `undefined` 不会抛 `InvalidArgsNumberException`，这条不算缺陷。**判定错误的部分**：缺 `<queries>` 导致 `resolveActivity` 全线失效（#3，这是本轮最"隐蔽但最致命"的一条）；`catch (_: Exception)` 把 `SecurityException`/`FileUriExposedException` 一起吞掉再裸启动 chooser（#6）；tree URI 缺 prefix 授权旗标（#8，会给用户一个空目录而不是报错，比报错更难查）；L2 用 ACTION_VIEW 却指望 EXTRA_INITIAL_URI 生效（#7）。另外 `openAutoStartSettings` 对显式组件用 `resolveActivity(Intent().setComponent(...), 0)` 探测，即使补了 `<queries>`，在没有 action/data 的裸 Intent 上做解析在部分 ROM 上也不稳，更稳的写法是 `getActivityInfo(ComponentName, 0)` 包 try/catch。

**5) 回归风险**

`git show HEAD -- src/app/viewer.tsx` 确认本轮只改了 3 个 hunk：import、`imageFullscreen` state、图片预览块替换 + 新增全屏层。下载主流程 `startDownloadAndExport`（选目录→冲突弹窗→两阶段流式下载→落盘→认领 document URI→写记录）**一个字符没动**，进度/网速节流（`:296-311`）、冲突三选一（`:237-272`）、`pickCreatedEntry` 认领真实 URI（`:346-355`）、已保存态两套渲染分支（`:445-477`、`:519-536`）均未受影响，因此"下载完成后完成态丢失""覆盖删目录"这两类历史事故的修复没有被回退。`share()`（`:383-397`）仍走 cache 里的 `file://` 副本 + expo-sharing，没有触碰 `content://`，所以 `SharingModule.kt:94` 的 scheme 硬校验不会在此路径复发——这一点容易被误判为回归，实际是安全的。真正的回归面有三处：图片预览容器从裸 `Image` 换成 `overflow:hidden` 的 `View` + 绝对定位子层，圆角从 Image 移到父容器（视觉等价，但 `aspectRatio:1` 下 4K 图会强制裁切，与之前一致）；新增的绝对定位层在滚动容器内的层级破坏（#2）；`record.fileSize` 取到陈旧 state（#18）。另外 `openFile/openFolder` 属于上一版已上线的路径，本轮未改，但 #6/#7/#21 说明它们的失败态提示一直缺失。

**6) 可维护性**

三处分层（`src/lib` 纯函数 / 组件只接线 / 页面只装配）方向正确，命名也基本诚实，但有四处"名不副实"：`clampScale` 的注释描述了不存在的 MIN_SCALE 兜底（#12）；`1 + 0.001` 这类浮点容差散落两处（#13）；`ZoomableImageFrame` 是无人部署的死代码（#15）；Kotlin 里 `attempt()` 的语义是"没抛异常"却被当作"成功打开"使用（#7 的根）。更结构性的问题是 `HermesKeepAliveModule.kt` 已经把两件无关的事塞进一个 302 行模块：前台服务保活状态机（start/update/stop/watchdog）与"外部应用跳转"（openFile/openFolder/battery/autostart）。前者关心的是 Android 的 FGS 记账规则，后者关心的是机型可见性与 URI 授权，错误处理风格也不同（前者有 `lastStartError` 诊断通道，后者只 return bool）。建议拆成 `ExternalIntents` 子模块，`openFolder` 的四层降级改成"返回实际命中的层号 + 失败原因"，既能让 JS 侧给出准确提示，也能让"文本断言式"的 Test 24 升级成对返回值的真断言。厂商 ComponentName 表（`:189-195`、`:250-275`）需要标注"采集机型/系统版本/采集日期"，否则半年后没人知道哪些还能用。
