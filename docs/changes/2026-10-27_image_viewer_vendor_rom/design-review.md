# 方案审查报告

审查对象：`docs/changes/2026-10-27_image_viewer_vendor_rom/`（requirements.md / tech-design.md / test-plan.md）
审查基准：`4aa83bd`（viewer）、`28b9425`（vendor ROM）、`6dc493b`（native openFile/openFolder）三笔已落地代码 + node_modules 实读 + AOSP / Android 官方文档原文。
审查立场：代码先于文档存在（`git status` 显示整个 `docs/changes/...` 目录未跟踪，代码已进 main），因此对每条论断按「先假设它是事后追认」处理，只认能被外部事实或源码证伪/证实的部分。

## 结论

**Conditional Pass** —— 方案的结构（分层、纯函数下沉、四层降级、逐层取证表）是真实工程产出，但**降级链与自启动探测的核心机制建立在两条错误的平台事实上**（`EXTRA_INITIAL_URI` 的适用 action、`resolveActivity` 在 targetSdk≥30 下的可见性过滤），平移边界这一"已知近似"的实际后果被从「整幅图可被拖出视野」降格描述为「拖到顶部留白」，四条高危问题全部落在 L2 静态断言的盲区里。文档当前形态不足以支撑"已论证闭环"，但代码可修，故不 Reject。

### 维度结论

- **论证闭环**：有系统性缺陷。文档的"求证方式"列只取证了**本地可读到的常量**（package.json、Sheet.tsx、_layout 行号、expo-sharing 行号——这几项我逐条核对全部属实），凡涉及**平台行为**的论断（`EXCLUSIVE` 语义、`EXTRA_INITIAL_URI` 适用范围、`resolveActivity` 可靠性、厂商组件名、APK 安装权限）全部只有结论没有证据链，且其中 3 条经原文核验为错。这不是"事后包装"的整体判断——分层与纯函数下沉是真实设计——但"二、方案论证（逐项证明可行性）"这个标题在平台侧名不副实，它证明的是"依赖存在"，不是"行为成立"。
- **事实准确性**：外部平台陈述错误集中在 F3/F4/F7（可见性过滤、`EXTRA_INITIAL_URI` 适用 action、安装权限），本地库陈述（expo-image 无手势、expo-sharing 行号、RNGH 依赖）全部正确。
- **完备性**：R1 ✔、R4 ✔、R8 ✔（未触碰下载逻辑，git diff 可证）；R2 ✘（F1+F2）、R5 ✘（F7）、R3 ◐（F8）、R6 ◐（F4/F5/F6）、R7 ◐（F3）。**R5 在 tech-design 里根本没有对应设计段**，只在 3.6 附带一句 MIME 推断；test-plan 也无对应 L1/L2/L3 用例——这是唯一一条"需求条目无方案、无测试"的完全遗漏。
- **风险识别**：见 F10。危险项与伪未知项混排、无严重度分级，是本方案最需要返工的一节。
- **可执行性**：分层代码可直接照做（`imageZoom.ts` 的纯函数签名清晰，另一个工程师能原样实现）；不可直接照做的是 3.7 每一层的"成功"判据（只判抛异常）与 3.8 的探测前提，照文档实现必然复现 F3/F4/F5。
