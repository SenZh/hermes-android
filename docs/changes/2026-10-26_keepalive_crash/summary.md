## 二、关键决策回溯

| 决策 | 备选 | 选它的理由 | 排除的理由 |
|-----|------|-----------|-----------|
| 三层防御（preflight + 首行提升 + 只上报看门狗） | 只把 `startForeground` 提到首行 | 能同时封住"异常路径不提升前台""stop 抢先""重复投递悬空"三条路径 | 单点修复仍会复现主因 |
| SAF 落盘传 `Directory` 而非 `new File(dir, name)` | 手删旧文件后 `copy(File)` | 前者由原生 `DocumentFile.createFile` 建真实文档；后者是伪子 URI，首次下载即抛异常 | 伪 URI 的 `exists()` 恒假，删除是空操作，`copy` 目标还会被解析成目录本身 |
| 启动决策下沉到纯函数 `decideStart` | 留在 `TurnEffects` 组件里 | 组件只能在真机上验证，而下沉后可被 vitest 全分支覆盖；审查实证"反转冷却门"这类变异只有这样才能拦住 | 组件内逻辑零自动化覆盖 |
| Kotlin 用 Robolectric 行为测试 | 继续用源码文本断言 | 文本断言分不清"先提升后停"与"先停后提升"——两者读起来是同一组调用 | 变异测试实证：9 组文本断言可被绕过 |
| 停服请求用带 TTL 的时间戳 | 布尔 + 锁 | 写端无条件写、读端自判新鲜度，消除跨线程 check-then-act；TTL 防僵尸标志 | 布尔方案存在丢 stop 或"下次提升后立刻自杀"两种错误 |

### 三条最贵的教训

1. **类型检查通过 ≠ 运行时语义正确**。`copy(finalDestFile, { overwrite: true })` 在 TS 与 Kotlin 签名上完全合法，但 SAF 下这个对象指向目录而不是文件。只有读 `SAFDocumentFile.documentFile` 与 AOSP `getTreeDocumentId` 才能发现。
2. **"测试全绿"可能只是"测试没测到"**。变异测试把 `stopOrDefer` 改回无条件 `stopSelf()`（正是崩溃形态），23 个套件全绿。文本层断言无法表达"顺序"这种运行时属性。
3. **自审标了高危却不写用例，等于没修**。我把 JS 侧两个修复标为"高"和"中"，却零断言覆盖，是审查方替我发现的。
